# FixSys API

## تشغيل التطوير

المتطلبات: .NET SDK 10 وPostgreSQL 17، أو Docker Compose.

```sh
cd backend
docker compose up --build -d
```

الـ API متاح على `http://localhost:8080/graphql`، وفحص الخدمة على `/health`.
لربطه بخادم Vite المحلي اضبط `FIXSYS_API_PROXY_URL=http://localhost:8080` عند تشغيل Vite.
انسخ `.env.example` في جذر المشروع إلى `.env.local`؛ قيمة `VITE_API_URL=/graphql` تستخدم proxy التطوير.
يمكن تشغيل API دون Docker بعد تجهيز PostgreSQL:

```sh
ASPNETCORE_ENVIRONMENT=Development ASPNETCORE_URLS=http://localhost:5099 dotnet run --project backend/src/FixSys.Api --no-launch-profile
```

الحسابان الافتراضيان للتطوير فقط: `admin@fixsys.sa / admin123` و`manager@fixsys.sa / manager123`.
في Development ومع تفعيل `Seed:DemoData`، تُضاف سجلات اختبار فعلية مترابطة مرة واحدة إلى الفرع الرئيسي، حتى لو كانت القاعدة موجودة مسبقاً. تشمل 6 عملاء وسيارات، 6 خدمات وقطع غيار، 3 موردين وطلبات شراء، 6 عروض أسعار ومواعيد، 4 أوامر تشغيل وفحوصات وفنيين، و6 موظفين وفاتورة جزئية السداد مع دفعة وكشف حساب. البيانات تحمل علامة `[تجريبي]` أو أرقام `DEMO-`، والتواريخ محسوبة عند التهيئة. يتوفر عرضان ينتظران الموافقة وطلبات شراء وأوامر تشغيل مفتوحة لاختبار Telegram. لا تُرسل رسائل تلقائياً ولا تُمسح البيانات الموجودة؛ إعادة التشغيل لا تكرر السجلات ولا تعيد قراراتها إلى الحالة الأصلية. لتعطيل الإضافة اضبط `Seed__DemoData=false`؛ لا تُنفذ في Production.

بعد تحديث مصدر الباك اند المحلي شغّل `docker compose --env-file telegram.local.env up -d --build api` ثم حدّث الواجهة أو اضغط **تحديث بيانات النظام**. التهيئة الحالية تستخدم
`EnsureCreated` عند عدم وجود migrations؛ لا ترقي قاعدة قائمة بهذه الطريقة. تغييرات مخطط
قاعدة قائمة تحتاج migrations ومراجعة قبل الإنتاج مع نسخة احتياطية.

## الربط والوحدات

`src/data/workspaceApi.ts` يحوّل GraphQL إلى نماذج الواجهة ويقرأ كل صفحات النتائج.
`LiveAppDataProvider` يحفظ في الخادم ثم يعيد القراءة؛ لا يستبدل فشل الاتصال ببيانات وهمية.
ترك `VITE_API_URL` فارغاً يفعّل النسخة التجريبية المحلية صراحةً.
العمليات تشمل العملاء والسيارات والخدمات والتصنيفات والقطع والمخزون والموردين
وأوامر الشراء والاستلام والمواعيد والفحوصات والقوالب وعروض الأسعار وأوامر التشغيل
والفواتير والدفعات والموظفين والأقسام والفنيين والأدوار والحسابات.
الصلاحيات المخصصة تُراجع من قاعدة البيانات عند عمليات الحفظ؛ صلاحيات القراءة المالية
والإدارة محمية كذلك. بيانات التشغيل المشتركة قابلة للقراءة داخل الفرع لتعبئة قوائم الاختيار.
الحذف العام ليس متاحاً للسجلات المالية؛ استخدم الإلغاء أو الإيقاف المتاح للوحدة.

## بريد OTP

إذا لم يضبط SMTP، يظهر الرمز في سجل Development فقط؛ في Production تفشل العملية
بدلاً من الادعاء بإرسال بريد. للإرسال الحقيقي اضبط متغيرات البيئة:

```text
Smtp__Host=smtp.example.com
Smtp__Port=587
Smtp__EnableSsl=true
Smtp__Username=your-account
Smtp__Password=your-secret
Smtp__From=no-reply@example.com
```

لا تحفظ كلمات المرور أو JWT keys في المستودع. أضف المتغيرات إلى خدمة API أو بيئة الحاوية.

## النشر

هذه البيئة تشغّل API وقاعدة تطوير محليين؛ نشر الواجهة وحدها لا ينشر ASP.NET أو PostgreSQL.
في الإنتاج شغّل خدمة API مستقلة، وPostgreSQL دائمًا مع نسخ احتياطية، وHTTPS.
اضبط `ConnectionStrings__Default` و`Jwt__Key` العشوائي (32 حرفاً على الأقل)
و`Cors__Origins__0` إلى أصل الواجهة، و`Seed__AdminEmail` و`Seed__AdminPassword`
لحساب الإدارة الأول على قاعدة جديدة، و`ASPNETCORE_ENVIRONMENT=Production`.
اضبط `VITE_API_URL` إلى عنوان GraphQL المنشور قبل بناء الواجهة، أو وجّه `/graphql`
إلى API عبر reverse proxy الإنتاج؛ Vite proxy خاص بالتطوير فقط.
# Telegram: محاكاة فعلية للأدوار الثلاثة

البوت المشترك محظور في مساحات التجربة المستقلة، ويُرفض تشغيل محاكاته في `Production`. يمكن لمسؤول كل مساحة ربط بوت خاص به من الواجهة، ولا يُسمح باستخدام نفس البوت في مساحتين.

من صفحة **الصلاحيات والمستخدمين → مختبر Telegram** يستطيع المسؤول ربط حساب واحد لاختبار شركة الشحن والعميل وموظف المركز. لا يمكن للبوت مراسلة حساب باسم المستخدم فقط: افتح رابط الربط المؤقت واضغط **Start** من الحساب المراد استخدامه، ثم اضغط **تحقّق من الاتصال**.

إعدادات **بيئة الباك اند فقط** (لا تستخدم `VITE_` ولا تحفظ السر في Git أو الدردشة):

```text
TELEGRAM_BOT_TOKEN=<new rotated bot token>
Telegram__SimulationEnabled=true
Telegram__StatePath=/persistent/private/telegram.json
```

في Docker Compose اضبط `TELEGRAM_BOT_TOKEN` و`TELEGRAM_SIMULATION_ENABLED=true` في بيئة التشغيل؛ ملف الحالة محفوظ على volume `telegramdata`. تشغيل الواجهة يتطلب `VITE_API_URL=/graphql` أو عنوان GraphQL الفعلي. لا تغيّر هذه الإعدادات الواجهة التجريبية إلى اتصال فعلي تلقائياً.

- البوت يستخدم long polling؛ يلزم اتصال HTTPS صادر إلى `api.telegram.org`، ولا يلزم webhook عام. استخدم بوتاً مخصصاً دون webhook، وشغّل **نسخة API واحدة فقط** لهذا البوت. هذا تنفيذ مختبر أحادي العملية، وليس نظام توزيع متعدد النسخ.
- الملف يحفظ الربط ومعرّف آخر تحديث وهاشات التذاكر فقط، وليس التوكن. حافظ على مساره الخاص وvolume دائم ونسخة احتياطية؛ فقدانه يستلزم إعادة الربط. التذاكر صالحة 10 دقائق للربط و24 ساعة لأزرار السجلات.
- اختبر بقاعدة بيانات اختبار: **تم التسليم** يستدعي الاستلام الحقيقي ويزيد المخزون. **موافق/غير موافق** يغيّران عرضاً مقدّماً وساري الصلاحية. أزرار الموظف تحدّث أمر تشغيل مفتوحاً.
- يُتحقق من صلاحيات المسؤول الحالية والفرع عند كل إجراء. Callback غير صادر عن المحادثة الخاصة المربوطة أو زر منتهي يُرفض. فصل الربط يلغي تذاكر الفرع. الأزرار القديمة لا تعيد فتح السجلات المغلقة أو تضاعف استلام المخزون.
- الأدوار الثلاثة هنا **محاكاة بحساب مسؤول واحد**؛ ليست صلاحيات عملاء أو ناقلين حقيقيين، ولا تصلح كإتاحة إنتاجية عامة دون ربط منفصل وهوية وصلاحيات لكل طرف.
- لا تعتبر إنشاء رابط أو اتصال الحالة دليلاً على تشغيل polling. دليل التشغيل: وصول رسالة Telegram، نجاح زرها، ثم ظهور التغيير عند تحديث بيانات النظام. لا تُسجّل عناوين طلبات Telegram لأنها تحتوي السر؛ تجنّب logging لطلبات HTTP الخارجية في أدوات مراقبة الخادم.

## تجربة العميل المستقلة

### بوت خاص لكل تجربة

افتح **الصلاحيات والمستخدمين → مختبر Telegram → خطوات تشغيل المحاكاة**. مسؤول التجربة ينشئ بوتاً جديداً عبر BotFather، ثم يدخل التوكن في حقل password داخل الموقع. `configureTelegramBot` يتحقق من `getMe` ومن عدم وجود webhook؛ لا يحذف webhook لخدمة أخرى. التوكن لا يعود في استجابة GraphQL ولا يُحفظ في LocalStorage أو SessionStorage. بعد الحفظ، أنشئ رابط الربط وافتحه واضغط Start ثم تحقّق من الاتصال.

بيانات البوتات تُحفظ باستخدام ASP.NET Data Protection في `/app/data/workspace-bots/credentials.protected`، ومفاتيح فكّها في `/app/data/protection-keys`، وحالة كل بوت في ملف منفصل باسم الفرع. volume `telegramdata` الحالي يحتفظ بها كلها. انسخ volume والمفاتيح معاً احتياطياً؛ حذف المفاتيح يجعل الأسرار غير قابلة للاسترجاع. التشفير هنا يحمي ملف الأسرار منفرداً؛ امتلاك الملف والمفاتيح معاً أو الوصول الإداري للخادم يتيح فكّه. استخدم KMS أو شهادة حماية المفاتيح عند نشر إنتاجي فعلي، ولا تسجّل GraphQL request bodies أو متغيراتها لأنها قد تتضمن التوكن.

`Telegram__AllowWorkspaceBots=false` يعطّل الربط الخاص؛ الافتراضي true. `Telegram__MaxWorkspaceBots` افتراضياً 50. يمكن تغيير مجلدات التخزين عبر `Telegram__WorkspaceStateDirectory` و`DataProtection__KeyPath`. شغّل نسخة API واحدة فقط؛ هذا worker محلي وليس نظاماً موزعاً. البوتات الخاصة تعمل حتى مع `Telegram__SimulationEnabled=false`، لأن هذا الخيار يخص البوت المشترك فقط. انتهاء التجربة يمنع إجراءات الرسائل فوراً ويزيل إعداد البوت خلال دورة التنظيف التالية (حتى دقيقة). حذف البوت الخاص من الموقع يوقفه ويزيل التوكن وتذاكره، ولا يحذف حساب البوت من Telegram.

كل تجربة تحاكي الأدوار الثلاثة على محادثتها الخاصة، وليست شبكة أطراف حقيقية؛ اختر بيانات اختبار. تأكد أن خدمة API تعمل باستمرار ولها قرص دائم؛ Render المجاني الذي ينام وقرصه مؤقت لا يصلح لحفظ هذه الأسرار أو لضمان وصول الأزرار. اضبط المسارات إلى volume خاص بصلاحيات مستخدم التطبيق، واستخدم HTTPS في الواجهة.

اضبط `TRIALS_ENABLED=true` في ملف بيئة Compose المحلي ثم أعد إنشاء خدمة API. تظهر في تسجيل الدخول دعوة إنشاء تجربة مستقلة: كل شركة تحصل على فرع معزول وبيانات تدريب مترابطة وحساب مدير خاص لمدة 7 أيام. كتالوج الخدمات والقطع والموردين والأدوار معزول أيضاً. انتهاء التجربة يمنع الدخول واستعمال JWT الموجود، ولا يحذف البيانات تلقائياً. الحد الافتراضي 50 تجربة نشطة و8 مستخدمين لكل تجربة؛ غيّر مدة التجربة والسعة عبر `TRIAL_DAYS` و`TRIAL_MAX_ACTIVE`.

النسخة الحالية لا تتحقق من ملكية بريد التسجيل ولا تحتوي CAPTCHA أو تنظيفاً تلقائياً لبيانات التجارب المنتهية. استخدمها كاختبار محدود الدعوات قبل الإطلاق العام المفتوح، ولا تدخل بيانات عملاء حقيقيين. مسؤول التجربة يدير بيانات شركته فقط؛ سجل التغييرات الإداري متاح عبر `auditEntries` ولا يحتفظ بقيم كلمات المرور أو أسرار الربط.

## تحديث قاعدة محلية موجودة بأمان

خذ نسخة احتياطية أولاً من PowerShell داخل `backend`:

```powershell
docker compose exec db pg_dump -U fixsys -d fixsys -Fc -f /tmp/fixsys-before-update.dump
docker compose cp db:/tmp/fixsys-before-update.dump ./fixsys-before-update.dump
```

لا تستخدم إعادة توجيه PowerShell 5 لمخرجات النسخة الثنائية. احتفظ بالنسخة خارج Git وخارج مجلد يتم نشره. حدّث `backend/src` و`Dockerfile` وملف Compose مع الإبقاء على ملف الأسرار المحلي ثم شغّل:

```powershell
docker compose --env-file telegram.local.env up -d --build
docker compose logs --tail=60 api
```

ترقية المخطط مخصصة للنسخة السابقة ذات الفرع الواحد؛ قاعدة قديمة متعددة الفروع تتطلب توزيع الكتالوجات يدوياً بدلاً من تخمين ملكيتها. الفواتير المكررة لأمر واحد أو أوامر التشغيل المكررة لعرض واحد تمنع إضافة قيد التفرد وتحتاج مراجعة قبل الترقية. الأوامر القديمة المكتملة لا تخصم مخزوناً بأثر رجعي؛ راجع أرصدتها قبل العمل الحقيقي. هذه ترقية توافق محددة وليست بديلاً عن خطة EF migrations كاملة للإنتاج.

## تشغيل دورة الورشة

الحجز يرفع الكمية المخصصة عند إنشاء أمر التشغيل. الإكمال يخصم القطع مرة واحدة ويسجل حركة صرف، والإلغاء يحرر الحجز. ابدأ التنفيذ قبل الإكمال؛ التسليم يتطلب فاتورة مسددة بالكامل. استلام أمر توريد جزئي قديم يحتاج مراجعة، ولا يُعاد استلامه كله لتجنب مضاعفة المخزون. ينتقل الخصم النقدي من العرض إلى صافي أمر التشغيل، وتُضاف الضريبة عند الفاتورة. `recordPayment` يقبل `requestId` ثابتاً لإعادة المحاولة دون تكرار نفس الدفعة؛ لا تغيّره عند إعادة محاولة الطلب نفسه.

```powershell
dotnet test .\backend\FixSys.slnx
npm run build
```

### تحديث النسخة المحلية دون فقد البيانات

نزّل ملفات المشروع المحدثة أولًا: تغييرات هذه البيئة لا تصل تلقائيًا إلى جهاز Windows. احتفظ بـ `telegram.local.env` المحلي وبنسخة قاعدة البيانات خارج المستودع. من مجلد `backend`:

```powershell
docker compose exec db pg_dump -U fixsys -d fixsys -Fc -f /tmp/fixsys-before-update.dump
docker compose cp db:/tmp/fixsys-before-update.dump ./fixsys-before-update.dump
docker compose --env-file .\telegram.local.env up -d --build
docker compose logs --tail=60 api
```

لا تستخدم `down -v` أو Factory Reset عند التحديث. إضافة `Users.SecurityStamp` جزء من ترقية التوافق؛ التوكنات القديمة التي لا تحتوي `session_stamp` ستتطلب تسجيل الدخول مجددًا. مفاتيح DataProtection وبيانات البوتات تحتاج volume دائمًا كما هو موضح أعلاه. روابط موافقة عروض Telegram القديمة قبل هذه الترقية تحتاج إعادة إرسال.

### متطلبات لم تُعتمد بعد

- تشغيل الاختبارات على PostgreSQL حقيقي، بما فيها طلبا سداد/استلام/حجز في نفس اللحظة، واختبار الاستعادة من النسخة الاحتياطية. استعلام تحقق ثم حفظ ليس وحده ضمانًا لمنع سباق العمليات.
- اختبار فعلي كامل من إنشاء تجربة مستقلة إلى التسليم، من حسابات متعددة، مع التأكد من CORS ورابط النفق الحالي؛ النفق المؤقت ليس استضافة دائمة.
- SMTP إنتاجي، حماية تسجيل التجارب العامة من الإساءة، وحدود GraphQL متعددة العمليات والأسماء المستعارة، وسياسة حذف بيانات التجارب والاحتفاظ بالنسخ الاحتياطية.
- مراجعة نظام الضريبة والعملة وترقيم الفواتير وفق بلد العميل؛ نسبة 15% الحالية ليست إعدادًا عامًا لجميع البلدان.
- استبدال ترقيات SQL المحددة بتاريخ migrations موثوق عند التحويل، واختيار webhook أو queue دائم لـ Telegram بدل polling متعدد الخوادم.

لا تعلن أن جميع هذه البنود نجحت بناءً على build أو اختبارات InMemory فقط. يجب الحفاظ على هذه الشروط والـ feature set عند اختيار أي استضافة أو تقنية بديلة.

## خيارات الاستضافة للنسخة الحالية

يمكن نشر الواجهة على Cloudflare Pages، وAPI كـ Docker web service على Render، وPostgreSQL على Neon. إعداد API: `ASPNETCORE_ENVIRONMENT=Production`، اتصال PostgreSQL مع TLS وفق مزوّد القاعدة، `Jwt__Key` عشوائي قوي، أصل واجهة محدد في `Cors__Origins__0`، `Database__AutoMigrate=true`، `Trials__Enabled=true` و`Telegram__SimulationEnabled=false`. على قاعدة جديدة اضبط حساب الإدارة الأول عبر `Seed__AdminEmail` و`Seed__AdminPassword` بأسرار خاصة. ابنِ الواجهة مع `VITE_API_URL=https://your-api-host/graphql` وأعد البناء عند تغيير العنوان.

خدمة Render المجانية قد تنام؛ أول طلب قد يتأخر، وليست مناسبة لعامل Telegram يعمل باستمرار. لا تعتمد على قرصها المؤقت أو قاعدة PostgreSQL المجانية محدودة العمر. اضبط SMTP حقيقياً للاسترجاع؛ أكواد Development المسجلة ليست خدمة بريد إنتاجية. يلزم نسخ احتياطي دوري خارج الخدمة واختبار استعادة قبل استخدام بيانات حقيقية. لا تنشر أسرار Telegram أو JWT باستخدام بادئة `VITE_`. Swagger وGraphQL IDE أدوات اختبار وليسا استضافة.
